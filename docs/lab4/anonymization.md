# Лаб.4, Завд.3: Right to Erasure та Anonymization Workflow (GDPR Art. 17)

Усі значення в документі синтетичні (демо-БД з вигаданими користувачами, `example.test`).

## 1. Терміни: чим анонімізація відрізняється від решти

| Термін | Що це | Наш приклад |
|---|---|---|
| **Маскування** | Значення лишається, але частково приховане для людей | `d***@example.test` у логах: дані в системі ті самі |
| **Псевдонімізація** | Ідентифікатор замінено на інший, але його можна зв'язати з людиною через окремий ключ. За GDPR це **досі персональні дані** | `email → user_4821` + таблиця відповідності; `sha256(email)` (детерміновано, підбирається словником) |
| **Анонімізація** | Зв'язок з людиною знищено **незворотно** | `login → anon-<16 випадкових hex>`, без збереженої відповідності |
| **Видалення** | Рядка більше немає | `cart`, `wishlist`, `computer_configurations` |

Нові значення в нашій реалізації **випадкові** (`secrets`), а не хеші: тому відновити початкове значення не можна навіть у принципі.

| `returns` | **SKIP** | за `user_id` | — | Застаріла порожня таблиця без FK: як repairs. |
| `sales` | **SKIP** | за `user_id` | — | Застаріла порожня таблиця без FK; маршрут /sales у коді посилається на неіснуючу таблицю clients. |

Чому в `keys` дія **ANONYMIZE**, а не DELETE: на `keys` посилаються 20 зовнішніх ключів, більшість із яких (зокрема `orders.user_id`) має
`ON DELETE NO ACTION`. Видалення рядка впало б на замовленнях, а замовлення (змодельовано як фінансовий запис) треба зберегти.
Тому рядок користувача **лишається**, але без жодного ідентифікатора, і бізнес-записи посилаються на «нейтральний» знеособлений запис.

Рішення про строки зберігання й правову підставу (чому саме замовлення лишається) організаційні; тут вони **змодельовані** правилом RETAIN.

## 3. Команда

`POST /api/users/{id}/anonymize` з `Content-Type: application/json` і тілом `{"confirm": "ANONYMIZE"}`. Не виконується простим GET.

| Код | Коли |
|---|---|
| **200** `anonymized` | роботу виконано; у відповіді лічильники рядків по таблицях (числа, без значень) |
| **200** `already_anonymized` | повторний запит: нічого не змінено (ідемпотентність) |
| 400 | немає явного підтвердження, або тіло не JSON |
| 401 | не автентифікований |
| **403** | чужий профіль для не-адміна; **однакова** відповідь для існуючого й неіснуючого `id` |
| 404 | лише для `admin`: такого користувача немає |
| 500 | збій у середині роботи: **транзакцію відкотено, нічого не змінено**, операцію можна повторити |

Доступ: власник або `admin` (та сама функція `check_access`, що й в експорті). Явне підтвердження й вимога `application/json` захищають від
**CSRF**: змінююча операція з cookie-автентифікацією не може бути викликана звичайною HTML-формою з чужого сайту (потрібен CORS-preflight),
а також від випадкового виклику.

## 4. Як це працює (`privacy/erasure.py`)

1. **Одна транзакція**: усе або нічого. При збої всередині відкочується ціле: напівзнеособленого стану не буває.
2. `SELECT ... FOR UPDATE` блокує рядок користувача: дві одночасні команди виконуються по черзі, друга бачить `anonymized_at` і нічого не робить.
3. Запам'ятовується **старий логін** (лише в пам'яті запиту): за ним знаходяться «похідні» записи без зовнішнього ключа (`registration_requests.guest_login`).
4. Сутності обробляються в порядку: `repair_status_history`, `software_status_history`, `config_components`, `orders`, `service_orders`, `repair_requests`, `software_requests`, `registration_requests`, `cart`, `wishlist`, `computer_configurations`, `product_reviews`, `user_activity_log`, `sql_execution_log`, `query_results`, `keys`. **Спершу дочірні**, бо вони знаходяться через батьківські рядки; `keys` останнім.
5. Нові значення: `anon-<16 hex>` для логіну (унікальність забезпечує `UNIQUE`), випадковий 64-символьний «пароль», якого ніхто не знає й не зберігає.
6. **Audit-подія пишеться в ТІЙ САМІЙ транзакції**: слід або є разом зі змінами, або немає ні того, ні іншого. Подія містить лише тип, `actor_id`, `subject_id`, результат і correlation ID, **жодного видаленого значення**.
7. Користувач, що анонімізував себе, одразу виходить із системи; для всіх інших живих сесій `load_user` більше не приймає неактивного користувача.

Два незалежні бар'єри від входу: `is_active = false` (вхід перевіряє це) і випадковий пароль, який нікому не відомий. Старий логін більше не існує, а новий не має відомого пароля.

## 7. Відомі межі

* **Резервні копії та вже видані експорти.** Анонімізація працює в живій БД. Резервні копії, вивантажені раніше файли й кеші поза системою потребують
  організаційної політики (строки зберігання бекапів). Відновлення з бекапу повернуло б PII.
* **Логи поза БД.** Старі рядки журналів застосунку (до Лаб.4 це були `print`) могли зберегти PII; нові логи знеособлені з самого початку.
* **Вільні тексти** прибираються цілком, бо PII в них розпізнати автоматично неможливо; корисний текст втрачається свідомо.
* **Записи без `user_id`** (наприклад, гостьове замовлення з тим самим email) не охоплені: у робочих даних таких немає.
* **Адміністратор** може анонімізувати будь-кого; обмеження «за яких умов» це процес, а не код. Кожен виклик потрапляє в audit.
* Рядок `keys` із випадковим логіном лишається: це «нейтральний системний запис», на який посилаються бізнес-записи. Він не містить PII, але факт існування облікового запису зберігається.
* **Робоча БД:** перед використанням на ній виконайте `python scripts/migrate.py` (додає `keys.anonymized_at` і `privacy_audit_log`).
