# ADR-0003: Операції з кількома записами виконуються в одній транзакції й ідемпотентно

- **Статус:** Accepted
- **Дата рішення:** 2026-11-27 (CCB-2026-11-27, [RFC-001](../../change/RFC-001.md))
- **Власник:** Загребенюк Б.
- **Зачеплені компоненти:** [Доступ до даних](../sdd.md#c-dal), [Операційні модулі](../sdd.md#c-routers)

## Контекст

`models.database.execute_query()` відкриває окреме з'єднання й робить COMMIT для кожного запиту. Тому функція з
кількома записами (UPDATE залишків + UPDATE статусу) не атомарна: збій або блокування посередині лишає половину змін.
Інцидент [INC-001](../../incidents/INC-001.md) показав і другу ваду: обробник не перевіряв стан перед зміною, тож
повторний POST під час «завислої» сторінки додав поставку до складу вдруге. Перевірка `tools/atomicity_check.py`
знайшла ще 16 функцій того самого класу (`.atomicity-baseline`).

## Розглянуті альтернативи

| Варіант | Плюси | Мінуси |
|---|---|---|
| Лишити `execute_query` і додати перевірку статусу | мінімальна зміна | збій між записами все одно лишає частковий стан |
| ORM із сесією (SQLAlchemy Unit of Work) | транзакції «за замовчуванням» | суперечить ADR-0001 (чистий SQL), переписування всього доступу до даних |
| **Unit of Work `transaction()` (Лаб.7) + блокування рядка `SELECT ... FOR UPDATE` + перевірка стану в тій самій транзакції** | атомарно й ідемпотентно; без нових залежностей; уже використовується в `privacy/erasure.py` | треба переписати функції поступово; більше коду на одну операцію |

## Рішення

1. Будь-яка операція, що змінює ≥ 2 рядки або таблиці, виконується в одному блоці `with transaction() as cur:`.
2. Операція, яку користувач або мережа можуть повторити (POST форми), спершу блокує рядок об'єкта
   (`SELECT ... FOR UPDATE`) і змінює дані лише з очікуваного стану. Повтор не змінює нічого й повідомляє «вже виконано».
3. Збій БД ловиться як `psycopg2.Error`, пишеться в журнал подією з ідентифікатором об'єкта (джерело алерту), а
   користувач бачить загальне повідомлення без тексту винятку.
4. Правило перевіряє pre-commit (етап 3, `tools/atomicity_check.py`). Старий борг записано в `.atomicity-baseline`,
   новий код без транзакції не комітиться.

## Наслідки

- Позитивні: клас дефекту INC-001 не може з'явитися в новому коді; старі функції мають виміряний список і план
  ([план супроводу](../../maintenance-plan.md#5-пріоритети-технічного-вдосконалення-legacy-компонента)).
- Негативні: транзакція з `FOR UPDATE` серіалізує паралельні дії над одним об'єктом (друга чекає першу). Для
  поставки це < 50 мс і бажано.
- Перевірка статична: вона рахує лише записи через `execute_query`. Сирий `cursor.execute` поза `transaction()` треба
  ловити рев'ю.
