# ADR-0002: Приватність як окремий модуль: анонімізація замість видалення, згоди за цілями, аудит без PII

- **Статус:** Accepted
- **Дата рішення:** 2026-10-10 (міграція `001_privacy_core.sql`, Лаб.4); **записано:** 2026-11-22 (Лаб.10)
- **Власник:** Загребенюк Б.
- **Зачеплені компоненти:** [Приватність](../sdd.md#c-privacy), [Безпечний журнал](../sdd.md#c-log)

## Контекст

Магазин зберігає персональні дані: логіни, email, ПІБ, телефони й адреси в замовленнях і заявках. Вимоги GDPR і
закону України про захист персональних даних: право на доступ (експорт), право на забуття, згода окремо для кожної
мети (маркетинг, аналітика) з можливістю відкликання, журнали без зайвих PII. Водночас замовлення, поставки й заявки
мають лишатися для бухгалтерії та статистики.

## Розглянуті альтернативи

| Варіант | Плюси | Мінуси |
|---|---|---|
| Фізичне видалення рядків (`DELETE FROM keys ...`) | дані справді зникають | ламає зовнішні ключі замовлень, заявок, новин; губиться облік продажів |
| М'яке видалення (`is_active = false`) | просто, FK цілі | PII лишаються в БД: це не забуття, а приховування |
| **Анонімізація в одній транзакції + згоди за цілями з історією + аудит без PII** | облік і FK цілі, PII замінено; згоду можна довести; аудит не стає копією PII | складніша логіка, треба знати всі місця PII (інвентар `docs/lab4/pii_inventory.md`) |
| Зовнішня платформа згод (CMP) | готові інтерфейси | залежність від стороннього сервісу, дані користувачів виходять за межі системи |

## Рішення

Окремий пакет `privacy/` з двома blueprint-ами (`privacy_bp`, `consent_bp`):

1. **Анонімізація** (`erasure.anonymize_subject`): у межах `transaction()` для кожної таблиці виконується дія з
   політики `privacy/policy.py`: ANONYMIZE (`keys`, `orders`, заявки й їхня історія, відгуки, журнали), DELETE (`cart`,
   `wishlist`, конфігурації ПК, `marketing_outbox`, `analytics_events`), RETAIN (`order_items`, згоди, аудит). Рядок
   `keys` лишається, бо на нього посилаються замовлення; `keys.anonymized_at` фіксує факт; повторний виклик ідемпотентний.
2. **Згоди** (`user_consents` + історія `user_consent_history`): ціль, версія політики, джерело; надати згоду може лише
   сам користувач; маркетинг іде через `marketing_outbox` з повторною перевіркою згоди перед відправкою.
3. **Аудит** (`privacy_audit_log`): лише тип події, хто, над ким, результат, correlation ID; жодних текстових полів для PII.
4. **Журнал** (`secure_logging`, `sanitizer`): маскування PII і секретів у всіх записах.

## Наслідки

- **Позитивні:** право на забуття виконується без руйнування обліку; згоди доводяться історією; журнал і аудит
  безпечно віддавати на аналіз; правила зосереджені в одному пакеті й покриті тестами (Лаб.4, 5, 7).
- **Негативні:** кожна нова таблиця з PII мусить потрапити в інвентар і в анонімізацію, інакше лишиться «дірка»
  (саме таку помилку моделював краш-тест Лаб.7); більше коду й тестів.
- **Правило супроводу:** нова колонка з PII = оновлення `docs/lab4/pii_inventory.md`, `privacy/erasure.py` і тестів
  в одному коміті.
