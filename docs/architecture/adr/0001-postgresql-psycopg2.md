# ADR-0001: PostgreSQL і чистий SQL через psycopg2 без ORM

- **Статус:** Accepted
- **Дата рішення:** 2025-10-17 (перший коміт проєкту); **записано:** 2026-11-22 під час аудиту документації (Лаб.10)
- **Власник:** Загребенюк Б.
- **Зачеплені компоненти:** [Доступ до даних](../../sdd.md#c-dal), [БД в ISD](../../isd.md#db)

## Контекст

Магазин має сильно зв'язану реляційну модель: товари, категорії, постачальники, замовлення з позиціями, гарантії,
заявки з історією статусів, контракти й поставки. Потрібні транзакції (замовлення списує залишки разом із записом
позицій), зовнішні ключі й звіти з JOIN та агрегаціями. Окрема вимога курсової: адміністратор має SQL-консоль і
бібліотеку збережених запитів, тобто виконує SQL прямо на робочій схемі. Команда: один розробник.

## Розглянуті альтернативи

| Варіант | Плюси | Мінуси |
|---|---|---|
| SQLite | нуль налаштувань, файл у репозиторії | слабка конкурентність записів, немає окремих користувачів і прав, інший діалект SQL, ніж у курсі БД |
| MySQL / MariaDB | поширена, проста | слабші CHECK і транзакційний DDL, менше типів (немає `timestamptz` у тому вигляді), курс БД вівся на PostgreSQL |
| **PostgreSQL + psycopg2 (чистий SQL)** | повний SQL, транзакційний DDL, `IF NOT EXISTS` для ідемпотентних міграцій, SQL-консоль працює з тією самою схемою | SQL пишеться вручну, немає вбудованого механізму міграцій |
| PostgreSQL + SQLAlchemy ORM + Alembic | моделі в Python, автоміграції | ще один шар абстракції й крива навчання; SQL-консоль і звіти все одно потребують сирого SQL |
| MongoDB | гнучка схема | дані за природою реляційні, немає JOIN і зовнішніх ключів, транзакції складніші |

## Рішення

PostgreSQL (зараз 18) як єдине сховище; доступ лише через `models/database.py` (`get_db_connection`, `execute_query`,
`transaction()`, `execute_query_resilient`) з **параметризованими** запитами psycopg2. Зміни схеми робляться
ідемпотентними SQL-міграціями `migrations/NNN_*.sql`, які застосовує `scripts/migrate.py`; знімок базової схеми
зберігається в `tests/db/schema_base.sql`.

## Наслідки

- **Позитивні:** SQL-консоль, звіти й застосунок працюють з однією схемою; цілісність гарантує БД (FK, CHECK); тести
  розгортають ту саму схему з дампу й міграцій (`tests/testdb.py`); транзакція замовлення атомарна (Лаб.7, 8).
- **Негативні:** SQL розкиданий по маршрутах (найбільше в `app.py`), рефакторинг схеми вимагає ручного пошуку
  запитів; ризик SQL-ін'єкцій контролюється лише дисципліною параметризації й code review; документ схеми швидко
  застаріває (аудит Лаб.10 знайшов документ з 23 таблицями при 45 реальних).
- **Що робимо з мінусами:** джерело правди схеми лише дамп + міграції; модель даних описано в SDD; нові запити йдуть
  у сервіси з контрактами (Лаб.8), а не в маршрути.
- Перехід на ORM вимагатиме нового ADR зі статусом, що замінює цей (superseded).
