# План CAPA для INC-001

**Коригувальна дія** (Corrective) усуває причину збою, що **вже стався**, щоб він не повторився. **Попереджувальна**
(Preventive) усуває причину **потенційного** збою, який RCA виявив, але який ще не стався. Причини — з
[Post-Mortem](postmortem-INC-001.md).

Трекер: issues з міткою `capa` у [kursova-docs](https://github.com/booooooo76/kursova-docs/issues?q=label%3Acapa); ланцюг
станів Open → In progress → Implemented → Verified (ефективність доведено) → Closed.

## CAPA-1 (коригувальна): атомарне й ідемпотентне приймання поставки

| Поле | Значення |
|---|---|
| Ідентифікатор | CAPA-1, [kursova-docs#2](https://github.com/booooooo76/kursova-docs/issues/2), реалізація — [RFC-001](../change/RFC-001.md) |
| Причина, яку усуває | 5 Чому, рівні 2–3: немає перевірки статусу; COMMIT на кожен запит; збій мовчазний |
| Опис | `apply_delivery()` в одній транзакції: `SELECT ... FOR UPDATE` → зміна залишків лише для `expected` → статус `received`. Збій БД → подія журналу `delivery_receive_failed`, алерт A5, runbook RB-002, загальне повідомлення оператору |
| Власник | Загребенюк Б. (розробник-власник модуля) |
| Дедлайн | 2026-11-27 (вікно RFC-001) |
| Статус | **Implemented**; перевірка ефективності триває до 2026-12-27 |
| **Перевірка ефективності** | 1) `tests/test_receive_delivery.py`: було 4 з 5 червоних (`pytest_fail.txt`), стало 6/6 зелених, зокрема відтворення INC-001 зі справжнім `LOCK TABLE` (`pytest_pass.txt`) — **виконано**. 2) `incident_sim.py`: сценарій блокування — надлишок 12 → **0**; сценарій збою БД — склад не змінився, A5 FIRING (`INC-001_simulation_pass*.json`, `ops_check_after_fault.txt`) — **виконано**. 3) 30 днів після релізу (до 2026-12-27): 0 розбіжностей складу на інвентаризації, кожна подія A5 закрита за RB-002 — **очікує** |

## CAPA-2 (коригувальна): обслуговування БД через RFC і `lock_timeout`

| Поле | Значення |
|---|---|
| Ідентифікатор | CAPA-2, [kursova-docs#3](https://github.com/booooooo76/kursova-docs/issues/3) |
| Причина, яку усуває | 5 Чому, рівень 4: блокування таблиці в робочий час без обмеження часу, без RFC |
| Опис | 1) Регламент CCB: обслуговування БД — завжди нормальна зміна, лише у вікні 21:00–23:00 UTC після резервної копії ([регламент](../change/ccb-regulation.md)). 2) `scripts/migrate.py` виконує кожну міграцію з `SET lock_timeout = '5s'`: якщо таблиця зайнята, міграція падає, а не вишиковує за собою всіх користувачів |
| Власник | Загребенюк Б. (SRE) |
| Дедлайн | 2026-11-27 |
| Статус | **Implemented**; аудит процесу — до 2027-02-25 |
| **Перевірка ефективності** | 1) `tests/test_migrate_lock_timeout.py`: відкрита транзакція користувача на `keys` → міграція падає з `LockNotAvailable` менш ніж за 10 с (фактично ≈ 1 с); на вільній таблиці міграція проходить — **виконано**. 2) Аудит за квартал (до 2027-02-25): кожен коміт у `migrations/` має issue `label:rfc` у стані Approved, створений раніше за коміт; ціль 100 % — **очікує** |

## CAPA-3 (попереджувальна): автоматична перевірка атомарності

| Поле | Значення |
|---|---|
| Ідентифікатор | CAPA-3, [kursova-docs#4](https://github.com/booooooo76/kursova-docs/issues/4), рішення — [ADR-0003](../architecture/adr/0003-atomic-multi-write.md) |
| Причина, яку усуває | 5 Чому, рівень 5 (процесна першопричина): DoD і хук не перевіряють атомарність. Потенційний збій: ще 16 функцій у 6 модулях (`add_delivery`, `edit_delivery`, `delete_product_permanently`, `confirm_config_to_cart`, `sql_console` …) можуть лишити частковий стан так само, як INC-001 |
| Опис | `tools/atomicity_check.py` — етап 3 pre-commit: нова функція з ≥ 2 записами поза `transaction()` блокує коміт; старий борг — `.atomicity-baseline` (16 рядків); пункт DoD у CONTRIBUTING |
| Власник | Загребенюк Б. (архітектор) |
| Дедлайн | перевірка — 2026-11-27; 6 функцій legacy-модуля — 2027-01-31; усі 16 — 2027-05-31 |
| Статус | **Implemented**; зменшення боргу за планом |
| **Перевірка ефективності** | 1) демонстрація: коміт нової функції з двома записами без транзакції блокується хуком (`capa3_hook_demo.txt`) — **виконано**. 2) Щомісяця: кількість рядків `.atomicity-baseline` не зростає й іде за планом 16 → 10 (2027-01-31) → 0 (2027-05-31). 3) 0 інцидентів класу «частковий запис» за 2027 Q1 |
