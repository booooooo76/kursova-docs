# Лаб.7, Завдання 3. Хмарний моніторинг і синергетична матриця Hotspots

## 1. Пайплайн CI/CD (GitHub Actions)

Файл `.github/workflows/quality-metrics.yml`. Запускається на кожен `push` і `pull_request` (і вручну:
`workflow_dispatch`). Робота виконується в Docker-контейнері `python:3.11` на хмарному раннері `ubuntu-latest`.

| Крок | Що робить | Навіщо |
|---|---|---|
| `actions/checkout@v4`, `fetch-depth: 0` | клонує репозиторій **з повною історією** | без історії `git log` не порахує churn (типовий checkout бере лише 1 коміт) |
| `git config --global --add safe.directory` | дозволяє git працювати в теці, створеній іншим користувачем | у контейнері тека належить не root, і git без цього відмовляється читати історію |
| `pip install lizard==1.24.1 radon==6.0.1` | ставить CLI-сканери **заново при кожному запуску** | чистий відтворюваний раннер; версії закріплені, як у `requirements-dev.txt` |
| `sh tools/ci_metrics.sh reports` | сканування, churn, матриця | той самий скрипт працює локально (Git Bash) і в хмарі |
| `$GITHUB_STEP_SUMMARY` | друкує матрицю Hotspots на сторінці запуску | видно без завантаження артефакту |
| `actions/upload-artifact@v4` | зберігає теку `reports/` як артефакт `quality-report` (30 днів) | машиночитаний звіт для подальшої аналітики |

Вміст артефакту:

| Файл | Формат | Що всередині |
|---|---|---|
| `lizard.csv` | CSV | кожна функція: NLOC, CCN, токени, параметри, файл, рядки |
| `radon_cc.json` | JSON | CC кожної функції й класу з рангом A–F |
| `radon_hal.json` | JSON | метрики Холстеда по файлах і функціях |
| `churn_90d.txt` | текст | коміти на файл за 90 днів |
| `hotspots.csv` / `.json` / `.md` | CSV / JSON / Markdown | синергетична матриця |
| `meta.txt` | текст | коміт, гілка, час, версії сканерів |

## 2. Code Churn з Git CLI

Обрано **варіант 1 (ретроспективний аудит власного проєкту)**: репозиторій має реальну історію з жовтня 2025 року,
з неї 32 коміти за останні 90 днів. Штучне наповнення історії не знадобилось.

Команда методички, обмежена 90 днями (`--since`):

```bash
git log --since="90 days ago" --format=format: --name-only | egrep -v '^$' | sort | uniq -c | sort -nr
```

| Частина | Що робить |
|---|---|
| `git log --since="90 days ago"` | коміти за останні 90 днів |
| `--format=format:` | порожній заголовок коміту (без хеша, автора, повідомлення) |
| `--name-only` | після кожного коміту список змінених файлів |
| `egrep -v '^$'` | прибрати порожні рядки між комітами |
| `sort \| uniq -c` | згрупувати однакові шляхи й порахувати, скільки разів файл зустрівся = у скількох комітах змінювався |
| `sort -nr` | від найчастіше змінюваних до найрідше |

Файли застосунку з найбільшим churn: `app.py` 8, `privacy/policy.py` 4, `privacy/erasure.py` 4, `routers/operator.py` 3,
`privacy/secure_logging.py` 3, `privacy/consent.py` 3, `privacy/api.py` 3.

## 3. Пороги категорій

* **Висока складність:** максимальний CC функції у файлі **> 10** (архітектурний ліміт методички й pre-commit хука Лаб.6).
  Береться максимум, бо регресії народжує найгірша функція, а не середня по файлу.
* **Висока мінливість:** комітів за 90 днів **більше за медіану** по файлах застосунку (медіана = 2, тобто 3 і більше).
  Поріг відносний: «частіше, ніж типовий файл цього проєкту», бо абсолютна норма залежить від темпу команди.

## 5. Аналіз і пріоритети на наступний спринт

**Червона зона (Hotspot) — рефакторинг у наступному спринті, у такому порядку:**

1. `app.py` — найчастіше змінюваний файл проєкту (8 комітів за 90 днів, 15 за всю історію) і водночас монолітний
   (1 365 рядків, Effort 10 817), з функцією `products` CC 13. Кожна нова фіча зачіпає цей файл, тож кожен його
   складний метод ризикує регресією. Дія: розбити `products` (фільтри й сортування каталогу) через таблицю параметрів
   фільтрації, як у Лаб.6; поступово виносити маршрути в `routers/`, щоб зменшити конфлікти паралельної роботи.
2. `routers/operator.py` — найгірша складність у проєкті (`edit_news` 21) і **чотири** функції понад ліміт, найбільший
   Effort (13 867). Дія: почати з `edit_news` і `operator_dashboard` (17), винести валідацію форм у дані.
3. `privacy/secure_logging.py` — `configure_logging` CC 13 у модулі, що активно змінювався в Лаб.4–5. Дія: таблиця
   налаштувань обробників замість ланцюжка умов.

**Жовта зона (Sleeping)** — `sanitizer.py` (17), `sql_queries.py` (20, три функції), `suppliers.py` (12, три функції).
Код заплутаний, але його майже не чіпають. Рефакторинг лише разом із першим Change Request до цих модулів.
Pre-commit хук Лаб.6 уже не дає їм погіршитись: усі ці функції записані в `.complexity-baseline` («храповик»).

**Зелена зона (Active)** — `erasure.py`, `policy.py`, `api.py`, `consent.py`: код Лаб.4–7, який постійно змінюється,
але лишається простим. Це ідеальний стан. Застереження: `processing_order` в `erasure.py` стоїть рівно на межі (CC 10),
і наступна правка його вже заблокує, тож його варто спростити заздалегідь.

**Сіра зона (Stable)** — решта: прості й стабільні утиліти, інфраструктура і конфігурація. Не чіпати.

**Висновок.** Жодна метрика окремо не дає цього пріоритету. За складністю першим був би `operator.py`, а `app.py` лише
третім (CC 13 < 21). За churn першим був би `app.py`, а `sql_queries.py` (CC 20) з'явився б серед найбезпечніших. Лише
поєднання показує, що найбільший ризик регресій там, де складний код ще й часто змінюють, а «сплячий» складний код
можна безпечно відкласти.

Обмеження: вікно 90 днів містить і коміти лабораторних робіт, тому churn модулів `privacy/` частково навчальний. Тести,
документація й службові скрипти до матриці не входять: аналізується лише код застосунку, як у Лаб.6.
