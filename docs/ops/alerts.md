# Каталог алертів моніторингу

Правило: **алерт без runbook — це шум.** Кожен рядок має умову, яку можна перевірити автоматично, серйозність,
відповідальну роль і посилання на інструкцію. Перевірки A1–A3 виконує `tools/ops_check.py` (Планувальник завдань
Windows, щохвилини; код виходу 1 = є FIRING).

| ID | Назва | Умова спрацювання | Серйозність | Відповідальна роль | Runbook |
|---|---|---|---|---|---|
| A1 | HealthDown | `GET /api/health` ≠ 200 (503 або немає з'єднання) три перевірки поспіль (3 хв) | SEV-1 | черговий L1 → L2 (адміністратор БД) | [RB-001](../runbooks/RB-001.md), крок 3, якщо `database: unavailable` за запущеної служби PostgreSQL |
| A2 | BackupStale | найновіший маніфест копії `D:\Backups\kursova\<db>_*.json` старший за 26 год (щоденна копія о 02:00 + 2 год запасу) | SEV-2 | L2 (адміністратор БД) | [RB-001](../runbooks/RB-001.md), розділ 7: позапланова копія `backup_db.py` |
| A3 | RestoreDrillOverdue | останній протокол `docs/ops/data/restore_drill_*.json` старший за 35 днів або має `result: FAIL` | SEV-3 | L2 (адміністратор БД) | [RB-001](../runbooks/RB-001.md), крок 3 (тестове відновлення) |
| A4 | ErrorBudgetBurn | витрачено > 50 % бюджету помилок будь-якого SLO з `docs/slo.yaml` (`tools/error_budget.py`, щодня) | SEV-3; 100 % → SEV-2 | SRE (власник SLO) | [політика бюджету](slo-policy.md#4-політика-витрачання-error-budget-policy) |

Зв'язок із RB-001: тригер «503 `database: unavailable`» = A1; «немає свіжої копії» = A2; «планова перевірка
копій» = A3. Ознаки алертів у виводі `ops_check.py` збігаються з ID цієї таблиці.

## Серйозність

| Рівень | Що означає | Реакція |
|---|---|---|
| SEV-1 | магазин недоступний або втрачаються дані замовлень | негайно, будь-який час доби |
| SEV-2 | функція частково не працює або під загрозою RPO / цілісність даних | протягом 1 год у робочий час |
| SEV-3 | ризик без поточного впливу на користувачів | наступний робочий день |

Час реакції і канали — [матриця ескалації](../maintenance-plan.md#3-матриця-ескалації).
