# Лаб.9, Завд.2 — Software Economics та Financial Quality Ledger

## Утиліта

`tools/financial_ledger.py` (Python 3, лише стандартна бібліотека). Тести: `tests/test_financial_ledger.py` (11 тестів, без БД).

| Вхід | Звідки |
|---|---|
| `ncloc`, `sqale_index`, ключ проєкту | сирий JSON SonarCloud із Завд.1 (`docs/lab9/report.json`), парситься щоразу, у коді цифр немає |
| `HOURLY_RATE` | змінна оточення, допустимо 35–50 $/год (поза діапазоном → помилка, код 2) |
| `OVERLOAD_COEFF` | змінна оточення, 1.3 |
| `DISCOUNT_RATE` | змінна оточення, 0.01 на місяць |

Запуск:

```powershell
$env:HOURLY_RATE="45"; $env:OVERLOAD_COEFF="1.3"; $env:DISCOUNT_RATE="0.01"
.\venv\Scripts\python.exe tools\financial_ledger.py docs\lab9\report.json
```

Код виходу: 0 = PASS, 1 = FAIL (не окупилось за 6 місяців), 2 = помилка вхідних даних. Отже, утиліту можна
поставити в CI як ворота якості.

Алгоритм:
1. `load_baseline` читає JSON, `load_rates` читає змінні оточення.
2. Тіло боргу = sqale_index / 60 × rate × overload; Cost of Delay = ncloc / 100 × rate.
3. Цикл `for t in 1..6`: коефіцієнт 1/(1+r)^t, дисконтований прибуток CoD × коеф., кумулятивна сума мінус тіло боргу
   = NPV_t. Перша ітерація з `NPV_t > 0` фіксується як точка окупності.
4. `render_ledger` пише `FINANCIAL_LEDGER.md` у корінь проєкту.

## Аналітичний висновок: як ncloc і SQALE впливають на окупність

Поділимо тіло боргу на Cost of Delay:

```
P / CoD = (sqale_index/60 × rate × 1,3) / (ncloc/100 × rate)
        = (TDD × ncloc × 0,5 × 1,3) / (ncloc / 100) = 65 × TDD
```

1. **Ставка `HOURLY_RATE` скорочується**: вона множить і витрати, і збитки, тому впливає на суми в доларах, але не на
   місяць окупності.
2. **ncloc теж скорочується**. Він лінійно збільшує обидві суми: великий Enterprise-проєкт і платить більше, і втрачає
   більше. Строк окупності визначає лише **щільність боргу TDD**, тобто співвідношення sqale_index і ncloc.
3. Окупність за 6 місяців можлива, лише якщо P < CoD × Σ 1/1,01^k = CoD × 5,795, тобто
   **TDD < 5,795 / 65 = 8,92 %**. Межа лежить усередині рейтингу B: усі проєкти з A окупаються за ≤ 6 місяців,
   проєкти з C — ніколи в цьому горизонті.
   - lear: 65 × 2,16 % = 1,40 місячних CoD → окупність на 2-му місяці.
   - Redis: 65 × 18,22 % = 11,84 місячних CoD → окупність лише на 13-му місяці.
4. Практичний висновок для Enterprise: великий абсолютний борг (у lear 365 людино-днів) не аргумент проти
   рефакторингу. Рішення ухвалюють за щільністю: при TDD до ~9 % повне погашення окупається за пів року. За вищої щільності
   борг гасять частинами, починаючи з модулів, де найбільше змін (Hotspots, Лаб.7), бо там Cost of Delay реально
   найбільший.

Обмеження моделі: правило «1 год на 100 рядків на місяць» не залежить від реального боргу (CoD однаковий і для
чистого, і для брудного коду того ж розміру), а рефакторинг вважається миттєвим. Тому модель оптимістична для
проєктів із малим TDD.
