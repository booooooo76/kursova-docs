# RB-001: відновлення бази даних з резервної копії

**Мета:** повернути робочу БД PostgreSQL у стан останньої перевіреної копії за **RTO ≤ 60 хв** із втратою даних не
більше **RPO 24 год**. Черговий виконує кроки по черзі; читати код застосунку не потрібно.

## 1. Тригер

| Подія | Звідки | Алерт з каталогу |
|---|---|---|
| `GET /api/health` повертає 503 `database: unavailable` три хвилини поспіль, а служба PostgreSQL запущена (БД пошкоджена, видалена) | моніторинг | **A1 HealthDown** |
| Логічне пошкодження даних (масове видалення, хибна міграція, некоректні залишки), яке не виправляється точковим SQL | скарга оператора, інцидент | A4 DataIntegrity (вручну) |
| Планова перевірка копій (restore drill) раз на місяць | розклад | **A3 RestoreDrillOverdue** |

Не застосовувати, якщо служба PostgreSQL зупинена (спершу `Start-Service postgresql-x64-18`) або 503 має
`migrations: missing` (тоді достатньо `scripts\migrate.py`, див. [ISD, порядок підняття](../architecture/isd.md#4-порядок-підняття)).

## 2. Передумови

- Права: локальний адміністратор Windows (керування службою), роль PostgreSQL `postgres` (пароль у `.env`, не
  друкувати), доступ до диска `D:\Backups\kursova` і до каталогу `OneDrive\KursovaBackups`.
- Інструменти: PowerShell 5.1, `venv` проєкту, PostgreSQL 18 (`C:\Program Files\PostgreSQL\18\bin`), openssl (Git for
  Windows). Для копії 3 — ключ `%USERPROFILE%\.kursova_backup_pass` (поза репозиторієм).
- Робочий каталог: корінь репозиторію Kursova.

## 3. Покрокові дії

Час на кожному кроці фіксується в журналі інциденту (UTC).

```powershell
# 0. Повідомити: застосунок переходить в обслуговування (канал #kursova-ops), зупинити застосунок (Ctrl+C у вікні app.py)
# 1. Зберегти поточний стан для розслідування, навіть пошкоджений (не обов'язково для повністю зниклої БД)
.\venv\Scripts\python.exe scripts\ops\backup_db.py --db computer_store --dest D:\Backups\kursova\forensic
# 2. Знайти останню копію та її маніфест (дата, розмір, SHA-256)
Get-ChildItem D:\Backups\kursova\computer_store_*.json | Sort-Object Name | Select-Object -Last 1 | Get-Content
# 3. Тестово відновити її в окрему БД і звірити (робоча БД ще не зачеплена); код 0 = PASS
.\venv\Scripts\python.exe scripts\ops\restore_drill.py --db computer_store
#    якщо локальна копія пошкоджена або диск D: недоступний - копія 3 з хмари:
$env:BACKUP_PASSPHRASE = (Get-Content "$env:USERPROFILE\.kursova_backup_pass" -Raw).Trim()
.\venv\Scripts\python.exe scripts\ops\restore_drill.py --db computer_store --from-offsite
# 4. Переключити застосунок на відновлену БД (робочу не видаляємо - вона потрібна для розслідування)
$env:DB_NAME = "computer_store_restore_drill"
.\venv\Scripts\python.exe scripts\migrate.py
# 5. Запустити застосунок
.\venv\Scripts\python.exe app.py
```

Після інциденту відновлену БД перейменовують на робочу у вікні обслуговування (`ALTER DATABASE ... RENAME TO`),
щоб повернути `DB_NAME` за замовчуванням; це окрема стандартна зміна.

## 4. Верифікація

1. `restore_drill.py` надрукував `"result": "PASS"`: SHA-256 збігся, `row_count_mismatches` порожній, таблиці
   міграцій на місці.
2. `Invoke-RestMethod http://localhost:5000/api/health` → `status: ok`, `database: ok`, `migrations: ok`.
3. Каталог `http://localhost:5000/products` відкривається, вхід оператора працює.
4. `.\venv\Scripts\python.exe tools\ops_check.py` → алерти A1-A3 у стані OK.
5. Дані після моменту копії (`created_utc` маніфесту) втрачені: оператор звіряє замовлення за цей проміжок з
   паперовими/поштовими підтвердженнями. Втрата ≤ 24 год = в межах RPO.

## 5. Відкат

Відновлення не руйнує робочу БД (крок 4 лише змінює `DB_NAME`), тому відкат — повернутися на неї:

```powershell
Remove-Item Env:DB_NAME            # знову computer_store з .env
.\venv\Scripts\python.exe app.py
```

Відкат застосовують, якщо перевірка кроку 4 провалилась або з'ясувалося, що робоча БД була лише недоступна, а не
пошкоджена.

## 6. Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| `restore_drill.py` FAIL на локальній копії | L2 (адміністратор БД) — перейти на копію 3 | одразу |
| FAIL і на копії 3, або відновлення не завершене за 30 хв | L3 (розробник-власник, Загребенюк Б.) | 30 хв від початку |
| Сукупний простій > 60 хв (порушено RTO) або втрачено > 24 год даних (RPO) | власник продукту: SEV-1, комунікація клієнтам | 60 хв |

Матриця ескалації та канали — у [плані супроводу](../maintenance-plan.md#3-матриця-ескалації).

## 7. Рівень автоматизації: 1 (скриптований)

| Рівень | Чи підходить | Чому |
|---|---|---|
| 0 — ручний | ні | ручні `pg_dump`/`pg_restore` з паролем у консолі — помилки в назвах БД, пароль у історії консолі |
| **1 — скриптований** | **так** | копія, перевірка SHA-256, відновлення в окрему БД і звірка рядків — у двох скриптах; людина лише вирішує, **коли** переключати застосунок |
| 2 — «одна кнопка» | поки ні | переключення робочої БД руйнівне й рідкісне (раз на квартал і рідше); помилкове натискання гірше за 5 хвилин ручної роботи; кандидат після того, як застосунок отримає staging |
| 3 — self-healing | ні | автоматично не відрізнити «БД пошкоджена» від «мережа недоступна»; самовідновлення затерло б дані після копії (втрата до 24 год) без рішення людини |

Плановий бекап (рівень 1 → 2): `backup_db.py` запускається Планувальником завдань Windows щодня о 02:00 —
[ISD, розділ 7](../architecture/isd.md#7-політика-резервного-копіювання).
