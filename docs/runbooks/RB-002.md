# RB-002: збій приймання поставки (алерт A5)

**Мета:** переконатися, що поставка, яку не вдалося прийняти, не змінила склад, і прийняти її, щойно БД
відновиться. Створено як CAPA-1 інциденту [INC-001](../incidents/INC-001.md).

## 1. Тригер

| Подія | Звідки | Алерт |
|---|---|---|
| у журналі застосунку подія `delivery_receive_failed` за останні 15 хв | `tools/ops_check.py` | **A5 DeliveryReceiveFailed** (SEV-2) |
| оператор бачить «Не вдалося прийняти поставку через збій бази даних» | скарга | A5 (вручну) |
| залишки не відповідають накладній після приймання | інвентаризація, скарга | вручну (див. крок 4) |

## 2. Передумови

- Застосунок пише журнал у файл у форматі JSON: `$env:LOG_FORMAT="json"; python app.py 2>> logs\app.log`.
- Права: роль operator або admin у застосунку; доступ до PostgreSQL (`psql`, пароль з `.env`, не друкувати).
- Інструменти: `venv`, `C:\Program Files\PostgreSQL\18\bin\psql.exe`.

## 3. Покрокові дії

```powershell
# 1. Які поставки й коли (delivery_id у полі події)
Select-String -Path logs\app.log -Pattern delivery_receive_failed | Select-Object -Last 5
# 2. Чи жива БД (якщо 503 database: unavailable - спершу RB-001 / розділ 6.3 ISD)
Invoke-RestMethod http://localhost:5000/api/health
# 3. Стан поставки та її позицій (підставити id)
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -d computer_store -c "SELECT delivery_id, status, delivery_date FROM supply_deliveries WHERE delivery_id = <id>"
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -d computer_store -c "SELECT di.product_id, p.name, di.ordered_quantity, p.quantity_in_stock FROM delivery_items di JOIN products p USING (product_id) WHERE di.delivery_id = <id>"
```

4. Рішення за результатом кроку 3:

| Статус поставки | Що означає | Дія |
|---|---|---|
| `expected` | транзакцію відкочено, склад не змінено (поведінка після RFC-001) | коли `/api/health` = ok, оператор натискає «Прийняти поставку» ще раз; повтор безпечний (ідемпотентно) |
| `received` | прийнято (можливо, повтором) | нічого не робити; повторне натискання не змінить склад |
| `expected`, але склад уже збільшено | лише для поставок, прийнятих до v1.1.0 (стара вада INC-001) | обхід з INC-001: `UPDATE products SET quantity_in_stock = quantity_in_stock - <кількість> WHERE product_id = <id> AND quantity_in_stock = <поточне значення>`, далі прийняти поставку штатно |

## 4. Верифікація

1. Поставка має статус `received`, `delivery_date` — сьогодні.
2. Залишок кожного товару = залишок до приймання + `ordered_quantity` (звірити з кроком 3).
3. `.\venv\Scripts\python.exe tools\ops_check.py` — A5 переходить в OK через 15 хв без нових подій.

## 5. Відкат

Приймання — одна транзакція, тож часткового стану немає і відкочувати нічого. Якщо поставку прийнято помилково,
це окрема операція обліку (накладна на повернення), а не технічний відкат. Ручний обхід із кроку 4 відкочується
зворотним `UPDATE` з тими самими числами.

## 6. Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| A5 повторюється для тієї самої поставки після відновлення БД | L2 (адміністратор БД): блокування `SELECT * FROM pg_locks WHERE NOT granted` | 30 хв |
| `/api/health` = 503 | L2 за [RB-001](RB-001.md) | одразу |
| розбіжність складу без події A5 (новий клас збою) | L3 (розробник-власник) + новий Incident Report | 4 год (SEV-2) |

## 7. Рівень автоматизації: 1 (скриптований)

Виявлення автоматизоване (A5 в `ops_check.py`), відновлення — повторне натискання, безпечне завдяки ідемпотентності.
Рівень 3 (автоматичний повтор) не обрано: якщо БД ще недоступна, автоматичні повтори створять шторм запитів
(Лаб.2, retry storm), а оператор однаково має фізично звірити накладну з товаром.
